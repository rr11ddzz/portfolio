The project and its place in the portfolio

This project models products and explores two interfaces: a console application for managing a product list, and a Swing interface for browsing a sample catalogue and building a cart.

It is included as supporting evidence of Java and object-oriented learning. The console and GUI use separate product models; this is not presented as one fully integrated shopping application.

Design and implementation

AreaWhat the source demonstrates
ObjectsProduct encapsulates brand, model, serial number and price. Electronics and Clothing extend it with category-specific fields.
CollectionsThe console uses an ArrayList of products with a 15-item limit, add/delete operations and list output.
InterfaceThe Swing prototype uses a JTable, category filtering, action listeners and a separate cart window.
PersistenceThe console includes plain-text save/load methods. Their formats need reconciliation before round-trip persistence can be relied on.

The source is preserved as supplied, including its early design choices. A useful review is to compare inheritance in the console classes with the separate, simpler Product class used by the GUI.

The original test plan covers adding both product types, capacity, deletion, empty/non-empty lists, saving, mixed-type reloads and invalid prices. It records expected behaviour, not verified test execution.

What is verified and what needs work

Source and the submitted test-plan document were inspected. The current review covers implementation and planned checks; it does not claim a fresh successful Java build or runtime test.

  • The console writer omits the product-type marker that the reader expects.
  • The GUI’s low-stock formatting replaces typed table values with strings, which conflicts with numeric casts in addToCart.
  • The details area and button panel both occupy BorderLayout.SOUTH.
  • The discount calculation counts distinct eligible categories rather than three products from the same category.

These findings make the next steps concrete; the prototype is not described as a completed retail application.

A focused improvement plan

  • Use one shared product model for both interfaces.
  • Define and test a consistent persistence format with an explicit type field.
  • Keep typed table data separate from visual formatting using a cell renderer.
  • Test cart totals, category discounts and input boundaries independently from the UI.
