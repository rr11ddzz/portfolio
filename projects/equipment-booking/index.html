The problem and scope

Support users who need to find equipment and submit reservations, while keeping equipment specifications and booking records organised. This Year 2 project uses Django templates, authentication and the ORM rather than a separate JavaScript front end.

The submitted coursework includes application source, project documentation and demonstration material. This case study links directly to the implementation so the data model and user workflow are easy to inspect.

From catalogue to reservation

StepCode behaviour
AccessRegistration creates an account. The login view checks the user’s ApprovalStatus before signing in.
DiscoverThe catalogue supports case-insensitive name search and ordering by fields such as name, type and availability.
ReserveA submitted booking stores the signed-in user, selected equipment and booking/return dates.
ReviewThe profile view retrieves reservations belonging to the signed-in user.

Equipment records reference device type, CPU, GPU and RAM models. Booking records link a user to equipment, with status and approval fields. InventoryCount, DeviceAudit and Report extend the data model; their presence should not be mistaken for fully implemented end-user workflows.

November 2026 · AI-assisted maintenance

Turning a review into tested fixes.

A later maintenance pass addresses concrete weaknesses in the original coursework. The original submission remains in repository history; the changes below were implemented and tested in November 2026 with AI assistance.

Original behaviourUpdated behaviour
Cancellation looked up any booking ID.Only the signed-in owner can cancel. The request requires POST and CSRF protection; cancellation preserves the record.
Dates were saved directly from request values.A server-side form rejects missing, malformed, past and reversed dates, with field-level feedback.
Reservations could overlap without checks.The application rejects conflicts with active bookings and unavailable equipment. Sequential cases are tested; simultaneous requests remain a separate deployment concern.
A fresh database had no demonstration equipment.A repeatable command creates three fictional catalogue items without creating users or shared passwords.

19 regression tests passed on Python 3.12, Django 5.2.19 and SQLite. Coverage includes approval, ownership, date boundaries, active and inactive booking states, CSRF and repeatable sample-data setup.

What is verified

The original reports and demonstration frames document the coursework interface. The updated reservation flow was verified through 19 automated Django tests on 11 November 2026; this was not a new full browser walkthrough or a production security audit.

The local database starts empty after migration. The sample-data command adds fictional equipment only. SQLite does not provide the row-locking behaviour requested by the booking transaction, so concurrent booking protection is not claimed. Administrative changes and shared deployment need additional validation.

Next development priorities

  • Verify simultaneous reservations against a deployment database and enforce consistent rules for administrative changes.
  • Add browser-level tests for the complete registration, approval, booking and cancellation journey.
  • Improve accessibility and add account-recovery support before shared deployment.
